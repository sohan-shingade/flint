# Flint v0.2 — Feature List for Industrial-Grade MVP

**Date**: 2026-03-20
**Research basis**: Freqtrade, QuantConnect/LEAN, Jesse, Hummingbot, Backtrader, Zipline, VectorBT, OctoBot
**Goal**: Make Flint usable by any Solana trader today — realistic backtests, paper trading, proper risk controls

---

## Current State (v0.1)

What Flint already has:
- 5 built-in strategies (MA Crossover, EMA Crossover, RSI, Bollinger, Momentum)
- Dynamic strategy loader with AST validation + Monaco editor in UI
- User strategy CRUD (save/load/delete/validate)
- Automated data collector with 90-day backfill + scheduled collection (oracle, funding, orderbook)
- DuckDB store with 5 tables (candles, funding_rates, oracle_prices, orderbook_snapshots, pool_snapshots)
- Backtesting engine with tearsheet generation (equity curve, drawdown, Sharpe, Sortino, monthly returns, buy-and-hold comparison)
- MEV framework (arb detection, liquidation scanning, JIT, bundle builder, simulator)
- Connectors (Drift, Jupiter) + Providers (Drift S3, Drift API, Jupiter, GeckoTerminal)
- FastAPI backend with 25+ endpoints
- React UI: Dashboard, Strategy Lab, Data Explorer, Docs, MEV Dashboard
- In-app documentation with learning path
- Comprehensive test suite

## P0 — Must Have (Trader Won't Trust the Platform Without These)

Every serious competitor has all of these. Without them, backtest results are unreliable and the platform can't be used beyond research.

### P0.1 — Strategy API Overhaul

**Why**: The current `on_candle(candle, history) → Signal` API is the simplest possible design. Every competitor (Freqtrade, QuantConnect, Jesse, Backtrader) provides per-trade risk controls, position sizing, and order management directly in the strategy. Without these, users can't express real trading logic.

**What to build**:

```
Strategy API v2
├── on_candle(candle, history, context) → Action (not just Signal)
│   context provides:
│   ├── context.portfolio        — current positions, equity, cash
│   ├── context.position(market) — current position for a market
│   ├── context.open_orders      — pending orders
│   ├── context.market_order(side, size)
│   ├── context.limit_order(side, size, price)
│   ├── context.stop_order(side, size, trigger_price)
│   ├── context.close_position()
│   ├── context.cancel_order(order_id)
│   ├── context.cancel_all()
│   └── context.log(message)
│
├── Strategy-level risk params (class attributes)
│   ├── stoploss          — e.g., -0.10 (10% loss)
│   ├── take_profit       — e.g., 0.20 (20% gain)
│   ├── trailing_stop     — e.g., 0.05 (5% trail)
│   ├── max_position_size — cap per trade
│   └── position_sizing   — "fixed" | "percent" | "kelly"
│
├── Optional callbacks
│   ├── on_fill(fill)           — called when an order fills
│   ├── on_funding(funding)     — called on funding rate update (perps)
│   ├── on_position_close(pos)  — called when a position closes
│   └── custom_stoploss(trade, current_price, current_profit) → float
│
└── Backwards compatible
    └── Old Signal-based strategies still work (adapter wraps them)
```

**Research source**: Freqtrade's `IStrategy` has 15+ callbacks including `custom_stoploss()`, `adjust_trade_position()` (DCA), `custom_stake_amount()`. QuantConnect's Algorithm Framework separates Alpha/Portfolio/Risk/Execution models. Jesse has the cleanest API — `should_long()`, `should_short()`, `go_long()`, `go_short()` with separate `stop_loss()` and `take_profit()` methods.

**Recommendation**: Follow Jesse's clarity but keep Flint's single-class simplicity. The `context` object pattern (like QuantConnect's `self.Portfolio`, `self.SetHoldings()`) gives users power without forcing framework complexity.

### P0.2 — Realistic Backtest Engine

**Why**: Current engine fills at bar close with flat fees and no slippage. Every competitor has pluggable fill/fee/slippage models. Traders who backtest with unrealistic fills get rekt in live trading — this is the #1 complaint across all platforms.

**What to build**:

```
Backtest Engine v2
├── Fill Models (pluggable)
│   ├── BarCloseFill       — current behavior (default for simplicity)
│   ├── NextBarOpenFill    — more realistic, fills at next bar's open
│   ├── SlippageFill       — configurable % slippage on market orders
│   └── OrderbookFill      — simulate against historical orderbook snapshots
│                            (you already collect orderbook data!)
│
├── Fee Models (pluggable, per-protocol)
│   ├── FlatFee            — current behavior (5bps default)
│   ├── DriftFeeModel      — maker: -2bps, taker: 10bps (tier-based)
│   ├── JupiterFeeModel    — per-route fees from quote API
│   └── CustomFeeModel     — user-defined
│
├── Order Types
│   ├── Market order       — fills next bar (with slippage)
│   ├── Limit order        — fills when price crosses limit
│   ├── Stop-loss order    — triggers market order at stop price
│   ├── Take-profit order  — triggers market sell at target
│   └── Trailing stop      — dynamic stop that follows price
│
├── Position Management
│   ├── Track entry/exit with multiple fills
│   ├── DCA (add to position on drawdown)
│   ├── Partial exits (scale out)
│   └── Margin / leverage tracking
│
├── Perp-Specific Simulation
│   ├── Funding rate payments (hourly, applied to open positions)
│   │   — You already have funding_rates table, just need to apply them
│   ├── Funding PnL vs trading PnL breakdown in results
│   ├── Liquidation simulation (if equity < maintenance margin)
│   └── Mark price vs oracle price tracking
│
└── Engine Controls
    ├── initial_capital (exists)
    ├── max_open_trades       — limit concurrent positions
    ├── position_size_mode    — fixed $ | % of equity | risk-based
    └── execution_delay_bars  — simulate latency (default: 1)
```

**Research source**: QuantConnect has separate `IFillModel`, `IFeeModel`, `ISlippageModel`, `IBuyingPowerModel` interfaces — each pluggable per brokerage. Freqtrade's `--timeframe-detail` uses smaller timeframes within candles for more accurate fills. Backtrader has bracket orders (entry + stoploss + takeprofit in one call).

**Data advantage**: Flint already collects orderbook snapshots and funding rates. No other local-first tool has this data pipeline for Solana. Use it.

### P0.3 — Paper Trading (Dry-Run Mode)

**Why**: Every competitor has this. It's the bridge between backtest and live. Without it, users go from simulated results straight to real money — a recipe for disaster.

**What to build**:

```
Paper Trading
├── Execution Mode
│   ├── Connects to real Drift/Jupiter APIs for live prices
│   ├── Simulates order execution locally (no real orders placed)
│   ├── Uses same strategy code as backtest (zero changes needed)
│   ├── Simulated wallet with configurable starting balance
│   └── Fills at current market price + slippage model
│
├── State Management
│   ├── Persist paper trades to DuckDB (new table: paper_trades)
│   ├── Track open positions, PnL, equity curve in real-time
│   ├── Resume after restart (read positions from DB)
│   └── Multiple paper sessions (named, with separate P&L)
│
├── UI Integration
│   ├── New page: Live Monitor (or extend Dashboard)
│   ├── Real-time equity curve (WebSocket or polling)
│   ├── Open positions with unrealized PnL
│   ├── Trade log (live, appending)
│   ├── Kill switch button (close all positions + stop strategy)
│   └── Strategy selector + start/stop controls
│
├── API Endpoints
│   ├── POST /paper/start   — start paper session
│   ├── POST /paper/stop    — stop paper session
│   ├── GET  /paper/status  — current positions, PnL
│   ├── GET  /paper/trades  — trade history
│   └── POST /paper/kill    — emergency close all
│
└── Architecture
    ├── Same strategy → engine → broker pipeline as backtest
    ├── Swap FileDataFeed for LiveDataFeed (Drift API polling)
    ├── Swap SimulatedBroker for PaperBroker
    └── QuantConnect calls this "backtest-live symmetry"
```

**Research source**: Freqtrade's dry-run mode is just `"dry_run": true` in config — same code path, simulated wallet. QuantConnect swaps `IDataFeed` and `ITransactionHandler` implementations. Jesse runs identical strategy code in backtest/paper/live. This architectural symmetry is the most important design principle across all platforms.

### P0.4 — Risk Management System

**Why**: Without automated risk controls, one bad trade can wipe an account. Every competitor provides these as first-class features, not afterthoughts.

**What to build**:

```
Risk Management
├── Per-Trade Controls (set in strategy class)
│   ├── stoploss             — fixed % stoploss per trade
│   ├── trailing_stop         — trail by N% once in profit
│   ├── trailing_stop_offset  — only start trailing after N% profit
│   ├── take_profit           — auto-exit at N% profit
│   ├── max_holding_period    — auto-exit after N candles/hours
│   └── custom_stoploss()     — callback for dynamic stop logic
│
├── Portfolio-Level Controls (set in config/engine)
│   ├── max_open_trades       — limit concurrent positions
│   ├── max_drawdown_pct      — stop all trading if portfolio DD exceeds N%
│   ├── max_daily_loss        — stop trading for the day if loss > N%
│   ├── position_size_limit   — max % of equity per position
│   └── total_exposure_limit  — max total leverage / exposure
│
├── Protection System (Freqtrade-inspired)
│   ├── StoplossGuard    — pause trading after N stoplosses in T minutes
│   ├── CooldownPeriod   — enforce N-minute gap between trades on same pair
│   ├── MaxDrawdown      — global kill switch on portfolio drawdown
│   └── Custom           — user-defined protection logic
│
└── Implementation
    ├── Risk checks run AFTER strategy signal, BEFORE order placement
    ├── Risk manager can modify, reject, or override orders
    ├── All checks apply in both backtest AND paper/live (same code)
    └── Logged: every risk intervention is recorded with reason
```

**Research source**: Freqtrade has `Protections` plugin system (StoplossGuard, MaxDrawdown, CooldownPeriod). QuantConnect has `IRiskManagementModel` with MaxDrawdownPercentPerSecurity, TrailingStopRiskManagement, MaxSectorExposure. Hummingbot has a kill switch that auto-stops on drawdown threshold.

## P1 — Expected (Users Expect These From a Serious Tool)

### P1.1 — Hyperparameter Optimization

**Why**: Freqtrade's Hyperopt and QuantConnect's optimizer are among their most-used features. Manually tuning strategy parameters is tedious and error-prone.

**What to build**:

```
Optimizer
├── Parameter Definition (in strategy class)
│   ├── IntParam(name, min, max, default)
│   ├── FloatParam(name, min, max, step, default)
│   ├── CategoricalParam(name, choices, default)
│   └── Used via self.params.name in strategy code
│
├── Optimization Methods
│   ├── Grid search       — exhaustive, all combinations
│   ├── Bayesian (Optuna) — smart sampling, converges faster
│   └── Random search     — baseline comparison
│
├── Objective Functions
│   ├── Sharpe ratio (default)
│   ├── Sortino ratio
│   ├── Total return
│   ├── Return / max drawdown (Calmar)
│   ├── Custom (user-defined function of BacktestResult)
│   └── Constraints: min trades, max drawdown cap
│
├── Execution
│   ├── Parallel backtests (multiprocessing)
│   ├── Progress reporting (% complete, best so far)
│   ├── Results table (all runs, sorted by objective)
│   └── Export best parameters
│
├── Anti-Overfitting
│   ├── In-sample / out-of-sample split (configurable ratio)
│   ├── Walk-forward mode (rolling train/test windows)
│   └── Display both in-sample AND out-of-sample results
│
├── API
│   ├── POST /optimize/run    — start optimization
│   ├── GET  /optimize/status — progress + best result so far
│   └── GET  /optimize/results — full results table
│
└── UI
    ├── Parameter range inputs in Strategy Lab
    ├── Optimization progress bar
    ├── Results table (sortable by any metric)
    ├── Parameter heatmap (2D: param A vs param B → Sharpe)
    └── Compare: best optimized vs default params
```

**Research source**: Freqtrade uses Optuna (Bayesian) with 10+ loss functions and parallel execution. QuantConnect has grid search with cloud parallelism. VectorBT can sweep 10,000 combinations in seconds using vectorization.

## P2 — Differentiators (What Makes Flint Competitive)

### P2.1 — Walk-Forward Testing

**Why**: The #1 complaint across all platforms is overfitting. Walk-forward testing is the gold standard for validating strategies but no local-first crypto tool implements it well. This is a genuine differentiator.

**What to build**:

```
Walk-Forward
├── Split data into N rolling windows
│   ├── Window 1: train [Jan-Jun], test [Jul-Aug]
│   ├── Window 2: train [Mar-Aug], test [Sep-Oct]
│   ├── Window 3: train [May-Oct], test [Nov-Dec]
│   └── ...
│
├── For each window:
│   ├── Optimize parameters on training set
│   └── Validate on out-of-sample test set
│
├── Report
│   ├── In-sample vs out-of-sample performance per window
│   ├── Aggregate OOS equity curve (the "true" performance)
│   ├── Parameter stability (do optimal params change wildly?)
│   └── Overfitting score (IS Sharpe / OOS Sharpe ratio)
│
└── UI
    ├── Configure: window size, step size, train/test ratio
    ├── Visual: windows on timeline, IS vs OOS bars
    └── Warning badge if overfitting score > 2x
```

**Research source**: QuantConnect supports this via scripted research notebooks. Freqtrade added `lookahead-analysis` and `recursive-analysis` as bias detection tools. No local-first crypto tool has proper walk-forward as a first-class feature.

├── API

## Data Storage Decision

**Recommendation: Keep single DuckDB file. No changes needed.**

Research confirms DuckDB is the optimal choice for local-first OLAP on time-series data:
- Columnar storage with compression (~0.3-0.5x raw size)
- Zero-copy Pandas/Arrow integration
- Native Parquet import/export
- No server process needed
- Handles 100+ markets × 2 years × 1-minute candles (~3GB) without issue

**Enhancements to add** (included in P1.4 above):
- Parquet export/import methods for backup and sharing
- Data metadata table for tracking coverage per market
- Gap detection for data quality

**What NOT to do**:
- Don't switch to PostgreSQL/TimescaleDB (adds server dependency, breaks local-first)
- Don't partition into multiple DB files (unnecessary at current scale)
- Don't switch to flat Parquet (loses transactional upserts the collector needs)
